## Objective

Turn heterogeneous evidence into a clear, defensible fraud-likelihood result.

## Core principle

Do not treat every signal as equally reliable.

Example:

```text
Dedicated AI detector
        = primary evidence

ELA

Metadata
        = supporting evidence

Cross-document mismatch
        = deterministic evidence
```

## Suggested score layers

### 1. Image Authenticity Score

```text
0 = highly suspicious
100 = highly authentic
```

Inputs:
- AI/deepfake model;
- ELA;
- noise;
- recapture;
- metadata.

### 2. Document Authenticity Score

Inputs:
- OCR consistency;
- metadata;
- tampering signals;
- field consistency;
- visual evidence.

### 3. Claim Consistency Score

Inputs:
- name;
- dates;
- amounts;
- IDs;
- document relationships;
- image timeline.

### 4. Overall Fraud Likelihood

Range:

```text
0 = low fraud likelihood
100 = high fraud likelihood
```

## Example

```text
Image authenticity       22
Document authenticity    64
Claim consistency        35
Identity match           96
```

The identity score should not automatically cancel strong fraud evidence.

## Explainability record

Each signal should preserve:

```python
{
    "check": "...",
    "category": "...",
    "severity": "...",
    "score": ...,
    "confidence": ...,
    "message": "...",
    "detail": {...}
}
```

## Example explanation

```text
HIGH FRAUD LIKELIHOOD — 74%

Primary indicators:
- AI-generation probability: 91%
- Document alteration indicator detected
- Claim amount differs from supporting invoice

Supporting indicators:
- ELA anomaly
- Metadata inconsistency

Identity:
- Face matches submitted ID
```

## Important safety rule

The score is a fraud-risk signal, not a legal determination.

Use language such as:
- "potentially manipulated";
- "suspicious";
- "high fraud likelihood";
- "secondary review recommended."

## Avoid false confidence

Do not display:

```text
100% FRAUD
```

unless the system has an explicitly justified deterministic rule and the product requirements truly support such a conclusion.

For model-based evidence, confidence should be described as model confidence/probability, not certainty.

## Configuration

Risk weights and thresholds should live in one configuration/policy location.

Avoid:

```python
if score > 63:
```

scattered across many files.

Prefer a centralized policy.

## Testing the risk engine

Test:
- no signals;
- one weak signal;
- one strong model signal;
- multiple supporting signals;
- conflicting signals;
- missing detector output;
- detector failure;
- missing metadata.

The same input evidence should produce the same result.

docs["10-NO-OVERENGINEERING.md"] = r"""# No-Overengineering Rules

## Project rule

> Build the simplest system that reliably satisfies the problem statement.

## 1. No architecture changes without a reason

Before changing architecture, answer:
- What requirement does this solve?
- What bug/problem does it remove?
- Why can't the existing design handle it?

If there is no strong answer, don't change it.

## 2. Prefer reuse

If VerifAI already has a working component and it is relevant:
- reuse it;
- adapt it;
- test it.

Do not rewrite it just because the code is not yours.

## 3. One responsibility, not one file per line of code

Create modules when they represent a real domain responsibility.

Do not create:
- wrappers around wrappers;
- unnecessary factories;
- excessive interfaces;
- one-function abstraction layers.

## 4. No unnecessary infrastructure

Do not add:
- Docker orchestration;
- Kubernetes;
- Redis;
- Kafka;
- microservices;
- message queues;
- cloud databases

unless an actual requirement demands them.

## 5. Model first, infrastructure second

The challenge rewards detection, risk logic, UI, architecture and innovation.

Spend time on:
- detection;
- evidence;
- scoring;
- explanation;
- demo reliability.

Do not spend hackathon time building infrastructure that does not improve those areas.

## 6. Avoid LLM overuse

Use deterministic code for:
- dates;
- amounts;
- IDs;
- exact comparisons;
- thresholds;
- known document fields.

An LLM should not be introduced just because the project is called AI.

## 7. Avoid duplicate logic

There should be one authoritative implementation for:
- risk thresholds;
- score calculation;
- evidence normalization;
- claim representation.

## 8. Fail gracefully

A single broken detector should not destroy the whole claim analysis.

Use:

```text
Detector failed
      ↓
Unavailable signal
      ↓
Continue remaining analysis
```

## 9. Don't optimize prematurely

First:
- correct;
- understandable;
- demonstrable.

Then optimize only if profiling shows a real bottleneck.

## 10. Don't refactor during the critical path

If working code solves the requirement:
- leave it;
- add a test;
- move forward.

Clean it after the MVP works.

## 11. Complexity budget

For every new component ask:

```text
Does this improve:
A. detection?
B. explainability?
C. reliability?
D. demo?
E. required architecture?
```

If none apply, it probably does not belong in the MVP.

## 12. Definition of done

A feature is done when:
- it works;
- it has a test/sample;
- its output is understandable;
- it does not break existing features.

Not when it has the most sophisticated architecture.
"""
